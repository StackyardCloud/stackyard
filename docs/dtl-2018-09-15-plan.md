# Azure Dev Test Labs (`dtl_2018_09_15`) Staged Plan

## Objective

Emulate Azure Dev Test Labs REST API (`api-version=2018-09-15`) with deterministic local behavior for:

- lab lifecycle and provider-level operation discovery
- artifact source/template/artifact and image/formula management
- user-scoped resources (users, disks, environments, secrets, service fabrics)
- VM, schedule, notification, policy, and virtual network surfaces
- an Azure Go SDK example under `examples/azure/dtl-2018-09-15`
- Azure coverage-script wiring for the new service key

## Contract Notes From Reviewed Method Pages

Cross-cutting traits:

- all reviewed methods require `api-version=2018-09-15`
- auth model is `azure_auth` OAuth2 (`user_impersonation` scope)
- shared error shape is ARM `ErrorResponse`
- list endpoints consistently return `value` with optional `nextLink`

Observed response-code patterns from method pages/spec:

- success statuses are drawn from `200`, `201`, `202`, `204`
- create/update methods are typically `200`/`201`
- action/long-running methods frequently include `202`
- delete methods commonly include `200` and idempotent `204` (`202` on async delete surfaces)
- every method includes a `default` error response

Notable behavioral areas to model carefully:

- VM action methods (`start/stop/restart/redeploy/resize/applyArtifacts/claim/unClaim`)
- schedule families at three scopes (`labs/*/schedules`, VM schedules, global schedules)
- user-scoped resource branches (`users/{userName}/...`) including disks, secrets, environments, service fabrics
- policy evaluation action (`PolicySets_EvaluatePolicies`) and notification dispatch action (`NotificationChannels_Notify`)

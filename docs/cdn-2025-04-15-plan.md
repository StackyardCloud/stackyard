# Azure CDN (`cdn-2025-04-15`) Staged Plan

## Objective

Emulate the Azure CDN ARM management API for `2025-04-15` with deterministic local behavior for:

- provider `operations`
- provider and subscription-scoped name-availability checks
- subscription-scoped resource usage and validate-probe utilities
- top-level `profiles`
- profile-scoped `endpoints`
- endpoint-scoped `origins`
- endpoint-scoped `originGroups`
- endpoint-scoped `customDomains`
- an Azure Go SDK example under `examples/azure/cdn-2025-04-15`
- Azure coverage-script wiring for the new service key

Important scope note:

- The reviewed Learn surface is the ARM management plane under `Microsoft.Cdn`.
- This is not the CDN or Front Door request-serving data plane.
- The `2025-04-15` surface is a hybrid management API:
  - classic CDN profile and endpoint resources
  - endpoint child resources such as origins, origin groups, and custom domains
  - provider-rooted utilities such as operations and name availability
  - migration-related profile actions tied to Azure Front Door Standard/Premium

Important staging note:

- The full provider operation list is broad, but the operation-groups page for `2025-04-15` is centered on:
  - `Check Name Availability`
  - `Check Name Availability With Subscription`
  - `Custom Domains`
  - `Edge Nodes`
  - `Endpoints`
  - `Operations`
  - `Origin Groups`
  - `Origins`
  - `Profiles`
  - `Resource Usage`
  - `Validate Probe`
- The staged plan below treats profile and endpoint CRUD as the core slice, then layers on endpoint children and utility/action routes.

## SDK Selection Note

- The official Azure Go SDK package for this surface is `github.com/Azure/azure-sdk-for-go/sdk/resourcemanager/cdn/armcdn`.
- The currently indexed typed clients are generated from older CDN API versions, but they still expose the main families needed for a practical example:
  - `ProfilesClient`
  - `EndpointsClient`
  - `OriginsClient`
  - `CustomDomainsClient`
  - `EdgeNodesClient`
  - `ResourceUsageClient`
  - `ManagementClient`
- The future example should therefore:
  - prefer typed `armcdn` clients for overlapping profile, endpoint, origin, custom-domain, and utility routes
  - use `azcore/runtime` only as a small targeted fallback if the local `armcdn` package does not expose exact `2025-04-15` operations such as migration flows or origin-group methods cleanly

## API Surface Summary

The reviewed pages expose six major route families:

- provider-level routes:
  - `/providers/Microsoft.Cdn/operations`
  - `/providers/Microsoft.Cdn/checkNameAvailability`
- subscription-scoped provider utilities:
  - `/subscriptions/{subscriptionId}/providers/Microsoft.Cdn/checkNameAvailability`
  - `/subscriptions/{subscriptionId}/providers/Microsoft.Cdn/checkResourceUsage`
  - `/subscriptions/{subscriptionId}/providers/Microsoft.Cdn/validateProbe`
- tracked top-level resources:
  - `/subscriptions/{subscriptionId}/resourceGroups/{resourceGroupName}/providers/Microsoft.Cdn/profiles/{profileName}`
- endpoint tree:
  - `.../profiles/{profileName}/endpoints/{endpointName}`
  - `.../endpoints/{endpointName}/origins/{originName}`
  - `.../endpoints/{endpointName}/originGroups/{originGroupName}`
  - `.../endpoints/{endpointName}/customDomains/{customDomainName}`
- profile and endpoint action routes:
  - `getSupportedOptimizationTypes`
  - `generateSsoUri`
  - `checkResourceUsage`
  - `start`
  - `stop`
  - `load`
  - `purge`
  - `validateCustomDomain`
  - migration actions under profile scope
- read-only inventory:
  - `edgeNodes`

Modeling implications:

- the emulator should keep one canonical profile store keyed by ARM ID
- endpoints, origins, origin groups, and custom domains should validate parent existence before mutation
- utility and action routes can be backed by deterministic fixtures derived from the stored profile and endpoint state
- the migration routes should be staged late because they are profile actions rather than foundational CRUD

## Contract Notes From Reviewed Method Pages

Shared management-plane traits:

- failures use ARM-style `ErrorResponse`
- list routes return `value`
- tracked resources use standard ARM fields such as:
  - `id`
  - `name`
  - `type`
  - `location`
  - `tags`
  - `systemData`
  - `properties.*`
- several mutating routes are long-running and document `202 Accepted` with a `location` header

### Operations and Utility Routes

Reviewed method pages:

- `Operations.List`
- `Check Name Availability`
- `Check Name Availability With Subscription`
- `Resource Usage.List`
- `Validate Probe.Validate Probe`
- `Edge Nodes.List`

Key traits from the reviewed pages:

- provider operations are read-only
- both name-availability routes accept `{name, type}` and return `nameAvailable`, optional `reason`, and optional `message`
- supported resource types for name availability include:
  - `Microsoft.Cdn/Profiles/Endpoints`
  - `Microsoft.Cdn/Profiles/AfdEndpoints`
- subscription resource usage returns profile-count quota and usage
- validate-probe accepts `probeURL` and returns `isValid`, `errorCode`, and `message`
- edge nodes are read-only POP inventory

Modeling implications:

- route behavior should be deterministic and mostly fixture-backed
- name availability should consult current stored endpoint names plus basic validation
- validate-probe can perform lightweight URL validation rather than real network checks

Key traits from the reviewed pages:

- profile CRUD is standard ARM resource management under resource-group scope
- profile actions return utility payloads rather than tracked child resources
- `List Resource Usage` is profile-scoped endpoint quota usage
- `List Supported Optimization Types` returns allowed endpoint optimization values
- migration actions are `POST` operations on existing profile context and should be modeled as state transitions rather than as new resources

Modeling implications:

- keep profile properties broad enough to cover both CDN and Azure Front Door flavored profiles, but do not over-model provider internals
- migration state can be represented with a small deterministic flag block in profile properties

Key traits from the reviewed pages:

Modeling implications:

- the first implementation slice should support endpoint create/get/list/update/delete plus start/stop
- load and purge can be deterministic action responses without simulating a full cache
- endpoint create should optionally seed nested origin/origin-group data if the request includes it

### Origins, Origin Groups, and Custom Domains

Reviewed method pages:

- `Origins.Create`
- `Origins.Get`
- `Origins.List By Endpoint`
- `Origin Groups.Get`
- `Custom Domains.Create`
- `Custom Domains.Get`
- `Custom Domains.List By Endpoint`
- `Custom Domains.Enable Custom Https`
- `Custom Domains.Disable Custom Https`
- `Custom Domains.Delete`

Key traits from the reviewed pages:

- these are endpoint child resources
- origins validate host name and port ranges
- origin groups represent origin references plus health-probe and failover settings
- custom domains support HTTPS enable/disable action flows and status-bearing properties

Modeling implications:

- child resources should be stored independently but keyed by normalized parent path
- HTTPS enable/disable is a clean deterministic state toggle that belongs in the initial custom-domain slice
- full TLS validation is unnecessary for the emulator; a documented status transition is sufficient

## Recommended State Model

Keep canonical stores for:

- profiles keyed by `{subscriptionId}/{resourceGroup}/{profileName}`
- endpoints keyed by `{subscriptionId}/{resourceGroup}/{profileName}/{endpointName}`
- origins keyed by `{subscriptionId}/{resourceGroup}/{profileName}/{endpointName}/{originName}`
- origin groups keyed by `{subscriptionId}/{resourceGroup}/{profileName}/{endpointName}/{originGroupName}`
- custom domains keyed by `{subscriptionId}/{resourceGroup}/{profileName}/{endpointName}/{customDomainName}`

Recommended fixture-backed adjunct state:

- provider operations list
- edge-node inventory
- subscription and profile resource-usage fixtures
- supported optimization-type fixtures
- generated SSO URI fixtures

Recommended derived behavior:

- endpoint host names derive deterministically from endpoint name
- profile and endpoint action routes update `provisioningState` and `resourceState` coherently
- custom-domain HTTPS actions toggle a small `customHttpsProvisioningState`/`customHttpsProvisioningSubstate` block

## Testing Strategy

Target focused lifecycle and validation tests rather than one giant end-to-end suite.

Minimum test coverage should include:

- provider operations and utility routes
- profile create/get/list/patch/delete
- endpoint create/get/list/start/stop/delete
- child-resource create/get/list/delete for origins, origin groups, and custom domains
- custom-domain HTTPS enable/disable state transitions
- validation failures for malformed names, missing required properties, and invalid probe URLs

Recommended negative cases:

- unsupported or malformed `type` in name-availability routes
- endpoint create without required origins
- origin create with invalid port range
- custom-domain validation with malformed host name
- migration action on missing profile

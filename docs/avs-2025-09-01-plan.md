# Azure AVS (`avs-2025-09-01`) Staged Plan

## Objective

Emulate Azure AVS for API version `2025-09-01` with deterministic ARM-style behavior under `Microsoft.AVS`, including:

- provider `operations`
- regional quota-style location actions
- `privateClouds` and their action routes
- private-cloud child resources such as `authorizations`, `globalReachConnections`, `addons`, `licenses`, `maintenances`, `scriptExecutions`, and `iscsiPaths`
- cluster-scoped resources such as `clusters`, `hosts`, `datastores`, `virtualMachines`, and `placementPolicies`
- workload-network subresources under `workloadNetworks/default/...`
- a typed Azure Go SDK example using the Azure AVS SDK
- Azure coverage-script wiring for the new service key

The AVS surface is broad enough that it should be implemented in mergeable slices grouped by route family and shared resource shapes, not as one large provider drop.

## Surface Summary

From the reviewed pages, the AVS control-plane surface clusters into these major areas:

1. Provider and regional actions
2. Private cloud lifecycle and cloud-level actions
3. Private-cloud child resources
4. Cluster-scoped lifecycle resources
5. Workload-network resources
6. Read-heavy inventory resources

High-value operation groups for the first implementation:
- `Operations`
- `Locations`
- `Private Clouds`
- `Authorizations`
- `Global Reach Connections`
- `Licenses`
- `Addons`
- `Maintenances`
- `Script Executions`
- `Clusters`
- `Hosts`
- `Datastores`
- `Virtual Machines`
- `Placement Policies`
- `Iscsi Paths`
- `Workload Networks`

Important shape observations from the reviewed pages:
- Almost every route uses standard ARM subscription/resource-group pathing with `api-version=2025-09-01`.
- Many write paths are modeled as create/update LRO-style routes even when deterministic local completion is sufficient for Stackyard.
- AVS has several action endpoints on top of resources, such as quota checks, maintenance rescheduling, password rotation, admin-credential listing, zone listing, and script execution creation.
- `privateClouds`, `clusters`, `datastores`, and `placementPolicies` have richer typed properties than a simple name/id envelope and should anchor the modeled fixtures.

## Contract Notes From Reviewed Pages

### Operations

`Operations.List` is the standard ARM provider-operations list:
- `GET /providers/Microsoft.AVS/operations`
- returns `OperationListResult`

Modeling implication:
- implement this first with a deterministic `value` list covering the resource families the provider will actually emulate.

### Private Clouds

Reviewed methods show:
- CRUD/list by RG and subscription
- PATCH update
- cloud-level actions such as admin-credential listing and password rotation

Create/update pages show stable core fields such as:
- `location`
- `identity`
- `properties.managementCluster`
- `properties.networkBlock`
- `properties.availability`
- `properties.internet`
- `properties.encryption`
- `properties.circuit`
- `properties.endpoints`
- `properties.provisioningState`

Modeling implication:
- `privateClouds` should be the canonical parent store.
- Start with a minimal but typed `properties` fixture containing management cluster, network block, endpoint values, and provisioning state.
- Action routes can mutate small deterministic subfields instead of trying to simulate real infrastructure side effects.

### Locations

The reviewed regional action is:
- `POST /subscriptions/{subscriptionId}/providers/Microsoft.AVS/locations/{location}/checkQuotaAvailability`

Modeling implication:
- return a deterministic quota object keyed by location.
- This is useful for examples and coverage because it avoids requiring a private-cloud prerequisite.

### Authorizations and Global Reach Connections

Reviewed pages show standard nested private-cloud child resources:
- express route authorizations via `authorizations/{authorizationName}`
- reach peering objects via `globalReachConnections/{globalReachConnectionName}`

Modeling implication:
- store these as child resources under private cloud.
- Example fixtures should expose IDs, names, provisioning state, and a few identifying properties such as peer circuit/resource IDs.

### Licenses, Addons, Maintenances, Script Executions, Iscsi Paths

These are mostly read/action or niche write resources:
- licenses support list/get
- addons at minimum support get/list-style inventory
- maintenances support filtered list and reschedule-style action
- script executions support create/get/list/delete
- iSCSI paths include a singleton-style `default` child path

Modeling implication:
- these are good Stage 2/3 targets after the parent private-cloud model exists.
- singleton resources like `iscsiPaths/default` should be handled explicitly, not through a generic collection helper.

### Clusters, Hosts, Datastores, Virtual Machines, Placement Policies

Reviewed pages show:
- clusters are nested under private clouds and support CRUD/list and `listZones`
- hosts are read/list under clusters
- datastores support typed create/get/list with multiple backing-volume shapes
- virtual machines are at least list/read inventory resources
- placement policies support typed create/update/list for discriminated policy property shapes

Modeling implication:
- cluster is the second major canonical parent.
- stage these after private clouds because most cluster-scoped routes depend on cloud existence.
- placement policies need at least a shallow discriminator implementation for `VmHost` vs `VmVm`.

### Workload Networks

The reviewed workload-network pages show a large nested namespace under:
- `/privateClouds/{privateCloudName}/workloadNetworks/default/...`

Examples reviewed include:
- `dnsZones`
- `vmGroups`
- `virtualMachines`

Modeling implication:
- workload-network is a large tail on its own and should be its own stage.
- first slice should focus on read/list routes plus one writable collection like `vmGroups` to validate nested routing and typed list envelopes.

Success criteria:

- unknown AVS routes fail with the repo’s standard Azure not-implemented behavior until implemented

### Stage 1: Provider Operations, Locations, and PrivateCloud Core

Implement first:
- `Operations.List`
- `Locations.CheckQuotaAvailability`
- `PrivateClouds` list by RG
- `PrivateClouds` list by subscription
- `PrivateClouds` get
- `PrivateClouds` create/update
- `PrivateClouds` patch
- `PrivateClouds` delete
- `PrivateClouds` list admin credentials
- `PrivateClouds` rotate NSX-T password
- `PrivateClouds` rotate vCenter password
- `PrivateClouds` get VCF license

Why first:
- these routes anchor the resource hierarchy
- they unlock the basic Azure Go SDK example flow
- they provide the highest coverage yield with the smallest number of canonical stores

### Stage 2: PrivateCloud Child Resources

Implement next:
- `Authorizations`
- `GlobalReachConnections`
- `Licenses`
- `Addons`
- `Maintenances`
- `ScriptExecutions`
- `IscsiPaths`

Modeling notes:
- keep child resources in maps keyed by `(subscription, rg, privateCloud, collection, name)`
- implement maintenance filtering parameters shallowly but deterministically
- script executions can be immediate-success fixtures with a stable execution result

### Stage 3: Clusters and Cluster Inventory

Implement next:
- `Clusters` CRUD/list
- `Clusters.ListZones`
- `Hosts` get/list
- `VirtualMachines` get/list

Modeling notes:
- clusters should include SKU, cluster size, provisioning state, and zone-related fields
- hosts and VMs can be read-only deterministic inventory resources generated from cluster membership

### Stage 4: Datastores and Placement Policies

Implement after cluster core:
- `Datastores` create/get/list/delete/update if present in the surfaced methods
- `PlacementPolicies` create/get/list/delete/update

Modeling notes:
- datastore properties should support at least one backing shape initially, with ANF volume being the simplest reviewed option
- placement policies need typed discriminator handling for policy properties

### Stage 5: Workload Networks

Implement as a dedicated stage:
- read/list routes for the major collections under `workloadNetworks/default`
- one or two writable collections first, especially `vmGroups`
- then broaden to DNS zones, segments, gateways, DHCP, NAT, and other NSX-style child resources if coverage requires them

Why isolated:
- this is the largest tail in the AVS surface
- it introduces deeply nested resource-specific schemas that are easier to validate once the parent cloud pathing is stable

## Validation Strategy

Provider tests should focus on:
- route dispatch correctness
- request validation errors for missing names/body fields
- deterministic resource lifecycle
- nested child-resource isolation per private cloud and cluster
- action endpoints returning typed success responses instead of empty generic payloads

Recommended tests:
- `TestAzureAVSOperationsAndPrivateCloudLifecycle`
- `TestAzureAVSPrivateCloudChildResources`
- `TestAzureAVSClusterInventoryAndPolicies`
- `TestAzureAVSWorkloadNetworkRoutes`
- `TestAzureAVSInvalidAPIVersionReturnsBadRequest`

Coverage goal for initial implementation:
- all AVS routes selected by the Azure endpoint coverage scripts succeed
- no implemented AVS endpoint returns `NotImplemented`
